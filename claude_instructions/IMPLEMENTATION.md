# Propagation engine: implementation write-up

This is the engine that replays the 2021 Conti campaign against a hospital network, before and after the agents' segmentation plan, and scores the clinical outcome. It doesn't include the Fetch.ai agents; teammates own those. The agents' only contact with this engine is the plan they hand in (section 8).

Everything is a **state-transition model**. A technique such as "credential dumping" is the name of a transition that flips a flag in a graph. The engine runs no attack code, issues no commands and contains no exploit detail.

---

## 1. Why build it this way (research summary)

| Source | What we take | What we leave |
|---|---|---|
| BloodHound (incl. OpenGraph custom edges) | identity edges: AdminTo, HasSession, MemberOf, trusts | static map, no time, no clinical layer |
| MulVAL logical attack graphs | precondition → effect rule format | vuln-scan inputs, state blow-up |
| Meta Attack Language (MAL / coreLang) | AND/OR steps, defense steps that block | probabilistic time-to-compromise (we replay deterministically) |
| CyberBattleSim | vulnerabilities as preconditions and side effects, cached credentials | toy networks, RL focus |
| CybORG / CAGE 4 | score on users' uptime, zones | Dec-POMDP machinery |
| MITRE ATT&CK / Attack Flow v3 | technique IDs as labels on our steps | nothing executable there anyway |
| Conti playbook leak (2021) | confirms step order: recon → creds → privileged accounts → trust-aware spread → encrypt | all tooling |
| Ghayoomi 2021, Willing 2025 | clinical processes degrade on IT loss; recovery lags differ by unit | no propagation |
| SIR / percolation | narrative and a baseline to beat | no credentials or trusts, so the wrong mechanism |

The novelty isn't the propagation. It's the join with clinical dependency, the leak-free backtest, and checking against real survivors (Hospital A, DoH).

## 2. Data model

**The engine is standalone.** It reads any organisation written in this format and knows nothing about the HSE. HSE, Cork and the British Library are test scenarios that check it. A scenario is a pre-incident snapshot (for Cork, 13 May 2021); the adversary lives in a separate file that planners never read.

```
nodes[]      id, dept, kind, os, windows, internet_exposed, medical_device,
             external (outside the hospital: HSE/NHN, Internet, SaaS), requires[]
links[]      a, b, layer="network"          # physical/logical connectivity
departments  id, switch                      # zone boundary candidates
domains[]    id, dcs[]                       # AD domains
trusts[]     a, b, direction                 # domain ⇄ domain
accounts[]   id, domain, tier, admin_to[] ("*" = whole domain, "*@X" = across trust), sessions_on[]
posture      av_mode, edr, mfa_remote_access, unpatched_edge, segmentation, backups
services[]   name, requires_all[], paper_fallback
levers[]     the moves a plan may make (section 8)
```

**Machine inventory (host profile).** Every node carries a `host` block describing what the machine is. These are the facts an asset inventory would hold, and the rules read them as preconditions:

| Field | Values | Used by |
|---|---|---|
| `os_family`, `os_version` | windows / vendor_embedded / appliance / none | which rules can apply at all; medical devices are vendor_embedded and never encrypt |
| `end_of_life` | true / false | patch levers can't fix EOL machines; only isolation or replacement |
| `domain_joined` | true / false | whether domain admin rights cover it |
| `endpoint_protection` | none / av_monitor_only / av_block_commodity / edr | R2 and R6 blocking; EDR lever |
| `patch_state` | per service class, e.g. `remote_access: unpatched_critical` | R1 edge variant; patch lever |
| `service_classes` | remote_access, file_share, admin, remote_desktop, directory, app, vendor | which zone allow-flows a plan must keep |
| `vendor_managed` | true / false | vendor VPN paths; who owns the fix in negotiation |

In the Cork scenario 48 of 95 nodes are end-of-life, which matches the pack's 45–55% Windows 7 share. All values are [S] and get regenerated by the robustness check (check 3).

**Four edge layers, one node set** (build a `networkx.MultiDiGraph` with `layer` on each edge):

| Layer | Edge | Built from |
|---|---|---|
| reachability | host → host, per port class | `links` + segmentation. Flat = any host reaches any host through SW-CORE |
| identity | account → host | `admin_to`, plus `sessions_on` (where credentials are cached) |
| trust | domain ⇄ domain | `trusts` |
| dependency | service/device → host | `requires`, `requires_all` |

Reachability is computed, not stored: `reach(u, v)` is true if a path exists in the network layer that no zone wall cuts for that port class. With no walls it's true for every internal pair.

## 3. State

```
node.level  ∈ clean < footholded < cred_holder < controlled < encrypted
node.flags  has_edr, av_blocking, patched, evicted
attacker    creds: set(account), privileges: set(account), domains_held: set
service     up | paper | down          # derived each step, never set
device      operational | dependency_outage   # medical devices never encrypt
```

Levels only rise through attacker rules. Only defender actions (D1–D3) lower them.

---

## 4. Rules

Each rule is `pre(state, x) → effect`. ATT&CK IDs are labels for the UI and log.

**R1 Initial access** (T1566 phishing | T1190 edge exploit)
- pre: x is an entry point (a mail-using workstation, or `internet_exposed`) ∧ ¬av_blocking(x). For the exploit variant, also `unpatched_edge[x]` and ¬mfa where creds would be needed.
- effect: x → footholded.

**R2 Credential harvest** (T1003)
- pre: level(x) ≥ footholded ∧ ¬av_blocking(x).
- effect: attacker.creds ∪= {a | x ∈ a.sessions_on}; x → cred_holder.

**R3 Escalate** (T1078)
- pre: some a ∈ creds has a higher tier than everything currently held.
- effect: privileges ∪= {a}. No new exploit: escalation just means using an edge that was already harvested. This is where "excessive privileges" bites.

**R4 Lateral movement** (T1021)
- pre: ∃ u controlled with reach(u, x) ∧ ∃ a ∈ privileges with x ∈ admin_to(a) ∧ level(x) < controlled ∧ ¬evicted(x).
- effect: x → controlled.
- This is the key rule. Network reachability **and** identity must both hold. Segmentation removes the first term; admin tiering or MFA removes the second.

**R5 Trust hop** (T1199)
- pre: attacker holds a privileged account in domain X ∧ trust X⇄Y ∧ some host of Y is reachable.
- effect: domains_held ∪= {Y}; accounts with `admin_to "*@Y"` become usable.

**R6 Detonation** (T1486)
- pre: campaign trigger time (01:00 14 May for the replay), or goal reached in variants.
- effect: every controlled x with ¬has_edr → encrypted. Reached backup stores are corrupted, which affects recovery only.

**Defender actions** (the only way down):
- **D1 Evict and reset** (Hospital A, 12 May): all org hosts → clean and `evicted`; invalidate creds of that org's accounts; cut inbound reach for the changed port classes.
- **D2 Endpoint protection** (DoH, 13 May, coverage "majority", so use ~0.9): has_edr on covered hosts.
- **D3 Disconnect** (HSE, 05:10 14 May): delete reachability across the cut. Any `requires` that crosses it → down.

**Clinical roll-up**, after every step:
```
for s in services:
    if any(level(h) == encrypted or crosses_cut(h) for h in s.requires_all):
        s = "paper" if s.paper_fallback else "down"
    else: s = "up"
device: dependency_outage if any requirement is encrypted or cut
```
A merely controlled host does **not** degrade service. HSE services ran normally from 7 May to detonation.

## 5. Campaign replay and the goal-driven attacker

- **Historical replay:** `data/scenarios/hse_conti_campaign.json` gives dated steps (entry, dormancy, escalation, hop order, detonation) and the three historical defender actions. The harness advances the clock. On each step it applies the named rule to the named target only if its preconditions hold. **A step whose preconditions fail is skipped and logged as "blocked by plan".** That's how the same campaign "goes nowhere" against the agents' plan.
- **Inside a hospital** (the host-level steps the campaign doesn't name): the attacker is goal-driven. Goal = control every host that a service with `requires_all` depends on, plus the DCs. Each step: pick the reachable, admin-able host that is closest to an unmet goal (shortest path in the combined graph), with the tie-break below. Detour budget: if blocked, try the next entry route (gateway → HSE trust → vendor VPN) before giving up. This is what lets the attacker adapt to a new layout instead of following a fixed script.
- **Variants** (judge's pick: door × goal) are new campaign files built on the same rules.

## 6. Determinism

- Fixed order per tick: R2 → R3 → R4 → R5, then the roll-up. R1, R6 and D1–D3 are dated events.
- Candidates sorted by `(distance_to_goal, domain, dept, node_id)`, which is a total order.
- Clock: day-level order from PwC; sub-day order authored once and committed.
- One RNG, seeded, used **only** by the synthetic-interior generator (check 3). Never on the replay path.
- Cache key = hash(scenario, plan, campaign, rules version). Bad venue Wi-Fi means the UI plays cached traces.

## 7. Outputs

```
trace[]   {t, rule, technique_label, node, from_level, to_level, reason}
services  timeline of up/paper/down per service
summary   orgs/hosts encrypted, services down, which campaign steps were blocked and by which lever
```
The Floor UI reads `trace` and the service timeline directly: amber = controlled, red = encrypted, violet = dependency outage.

## 8. Interface to the agents (no agent code here)

The agents produce a plan from the snapshot only. The engine accepts:
```json
{"plan_id":"...", "levers":[
  {"id":"segment_departments", "zones":{"rt":["rt"],"rad":["rad"],"dc":["dc"]},
   "allow":[["rad","dc","imaging"],["rt","dc","oncology"]]},
  {"id":"cut_hse_trust"}, {"id":"tier_admin_accounts"}, {"id":"edr_servers"}]}
```
Lever IDs are listed in each scenario's `levers`. The engine applies them to the snapshot, then runs the campaign. Allow-flows are the "must-keep" links clinical agents argue for; a plan that drops one shows up as a service going down even with no attack. That gives the negotiation its friction.

## 9. Verification (what to run, in order)

Expectations are in `data/tests/calibration.yaml`. Ground truth is in `data/ground_truth/`.

1. **HSE calibration** (org level): spread order K,D → J → C,L → A → B; encrypted HSE,C,K,D,L,J,B; not encrypted A, DoH; ≥33 privileged accounts by 13 May; dormancy fires no rules.
2. **Right reasons:** remove D1 and A gets encrypted; remove D2 and DoH does. The baselines "encrypt everything reached" and SIR on the reachability graph must get A or DoH wrong.
3. **Robustness:** regenerate the CUH interior over 100 seeds (sessions, DA placement, OS mix within the pack's ranges). Report the share of seeds in which each press outcome holds. This is the honest statistic.
4. **CUH press hold-out:** freeze rules, run once, compare to `cuh_press_outcomes.csv`.
5. **Out of sample:** British Library scenario, frozen rules, run once. Expect servers encrypted, laptops and desktops not, cloud finance up.

**Leakage rules:** planners never read the campaign file or ground truth; the interior generator is committed before checks 4 and 5; no rule changes after seeing a hold-out result without saying so.

**Scoring caveat:** not every trusted org was attacked (E, H, N show no evidence). Target choice comes from the campaign file, so score org outcomes **conditional on being targeted**. Untouched orgs are not negatives for the rules.

## 10. Known limits to say out loud

- Radiology and email fail under any local plan because the HSE cut the national network at 05:10 (check 6).
- With ~10 org labels from one campaign, this is calibration plus falsification, not statistical validation. 8 of 10 targeted orgs were encrypted, so a trivial rule scores 80%; the test that matters is A and DoH.
- Every device, account and path inside CUH is reconstructed [S]. Only the name and the press outcomes are real [P].

## 11. Suggested build order

1. Loader + graph build + `reach()`.
2. R1–R6, D1–D3, roll-up; HSE org-level replay passes check 1.
3. Ablations and two baselines (check 2).
4. CUH host-level replay with the goal-driven attacker; plan application; trace export for the Floor UI.
5. Seed generator and check 3; then checks 4 and 5 once, frozen.

Stack: Python 3.11, networkx, pydantic for the schema, pytest reading `calibration.yaml`; FastAPI WebSocket to stream `trace` to the existing HTML console.
